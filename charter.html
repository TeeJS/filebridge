Charter

1

The one thing it must do

Run every FileBridge job (folder, Google Drive, web-drop) on its schedule from its own app, managed in its own normal desktop window, while the Panel can still show what it is doing.

2

What would be wrong if it "worked" without these

  • One scheduler only. If the old drop-in and the new app both run the same jobs, files copy twice and mirror jobs delete twice. The cutover must make that impossible, not just unlikely.
  • No lost state. Jobs, lifetime stats, grand totals, filter groups, rule files, seen-ledgers and last results all come across.
  • Same data safety. Safe replace, the mirror test-source guard, Recycle Bin and skip-pattern protection keep working unchanged.
3

Off-limits as workarounds

  • Rewriting the engine or UI. sync.js, drive.js, web.js, server.js, app.js and index.html move over as they are, with only the edits listed below.
  • A localhost web server for the app's UI or for status (EDR rule #16).
  • "Copy jobs.json by hand" as the migration path.
  • Any controls in the Panel monitor.
  • Shipping site-specific web-drop rules.
4

Deployment target and backup location

  • Target: Windows 11, signed with Azure Trusted Signing and released through GitHub Actions (the electron-signed-release skill). macOS and Linux are out of scope for v2.0.
  • Code: a new repo TeeJS/filebridge at D:\Github\filebridge, created from the drop-in's git history. Git is the backup.
  • User data: the import never deletes the old folder. Its jobs.json is renamed jobs.migrated-<yyyymmdd-hhmmss>.json and left in place.

Host seams and what replaces them

Today the drop-in leans on Bedrock Panel in four places. The new Electron shell supplies each one.

Today (Bedrock Panel host)Standalone replacement
/app-api/<action> HTTP route to handle()A privileged filebridge:// protocol registered with protocol.handle. The page's existing fetch('/app-api/…') calls resolve against it, in-process. No socket.
/app-host/pick-folderThe same protocol route, answered with dialog.showOpenDialog.
ctx.oauth (status, connect, disconnect, token)Port src/auth/oauth-handler.js and token-storage.js (MIT) with one Google provider. Tokens and the client secret are encrypted with raw Windows DPAPI, using Bedrock Panel's own binding. Changed in step 2 from safeStorage: the Panel found its key didn't survive across launches.
Serve the page and serverAutoStartBrowserWindow loads filebridge://app/index.html, and server.js loads at startup so schedules arm immediately.

The Electron calls FileBridge already makes directly (sign-in windows, session partitions, Recycle Bin, .lnk resolution, open folder) work unchanged.

EDR notes The only listening socket is the OAuth loopback callback, open only while you click Connect for Drive. Google desktop clients require a loopback redirect. It uses an OS-assigned port instead of the Panel's fixed 5173, so the two apps can't collide. "Start with Windows" uses the standard per-user Run entry. It is off by default. No shell spawning, no downloaded executables.

Edits to the moved code

This is the complete list.

  1. server.js: DATA_DIR becomes the app's own data folder. openWindow and its 127.0.0.1 origin check are removed, since the app already is the window.
  2. app.js / index.html: default to the window layout. Remove the editor-embed code and the 1920×480 panel layout.
  3. Drive chip: add Change client…. This fixes the 2026-10-01 blocker: after the Google projects were deleted, a dead stored client left the UI with no way to enter a new one.
  4. New status.js, which writes status.json.
  5. New import.js, the first-run migration.

status.json contract (v1)

  • Written atomically (temp file, then rename) on run start and end, on job and settings changes, and at most once per second during a run. A heartbeat rewrites it every 30 s.
  • Fields: schema: 1, appVersion, heartbeatAt, paused, and current (job, kind, phase, current file, files and bytes done/total, rate, the up-to-date · copy · filtered tally, paused state). Then queue, per-job rows (name, kind, enabled, next run, last run's result, copied, bytes, errors, warnings) and grand totals.
  • No secrets, tokens, cookies or rule contents. Local paths are fine.

Migration on first run

  1. If %APPDATA%\bedrock-panel\file-bridge\jobs.json exists and the new data folder is empty, the app offers Import from Bedrock Panel.
  2. It copies everything across: jobs, filters, rules, ledgers, results and the log.
  3. It renames the old jobs.json to jobs.migrated-<timestamp>.json. The old drop-in then finds no jobs and schedules nothing, even before its update lands. This is how the single-scheduler rule is enforced.
Expected re-dos (the app says so when they come up) Drive: a new Google client and Connect. The 2026-10-01 project deletion forces this anyway, and the Panel's tokens aren't portable. Web-drop sites: one fresh sign-in each. Sessions live in Bedrock Panel's Chromium profile, and I expect its cookie encryption to block copying them across.

Panel monitor

  • Same app id (file-bridge). Your existing FileBridge page turns into the monitor through Check for updates, with no page to re-create. Version bump plus rebuilt zip and index, per the drop-in rule.
  • server.js shrinks to one read-only status action that reads status.json. No scheduler.
  • The page shows the live run band (job, file, progress, rate, tally), next runs, last results and grand totals. It shows "FileBridge isn't running" when the heartbeat is more than 90 s old, and keeps the last-known state visible.
  • No buttons that change anything. Designed to the panel design system.

Order of work

Each step is reviewed before the next one starts.

  1. Repo. Create D:\Github\filebridge from the drop-in's history (git subtree split), then add an Electron 44 + electron-builder skeleton on the same versions Bedrock Panel uses.
  2. Shell. Move the data folder first, so the engine can never load against the Panel's jobs. Then main.js with a single-instance lock, a tray icon (closing the window keeps the scheduler running), the filebridge:// protocol, the folder picker, the OAuth port and the login item.
  3. De-host edits. Items 1–3 above. test.js carries over and must pass.
  4. status.json and import, with new node:test coverage for the writer, schema, heartbeat, and the import and rename.
  5. Adversarial review of the shell, import and status writer, as every FileBridge release has had.
  6. Signed release v2.0.0 through GitHub Actions. You review the release notes before anything is published.
  7. Your live test of the app: import, then one run of each job kind.
  8. Panel monitor. Convert the drop-in, verify it in the harness, merge, then you update it through Check for updates. This is last on purpose: if the monitor ships first, your jobs stop running until the app is installed.

Done when

  • The installer is signed, and Get-AuthenticodeSignature reports Valid.
  • Import brings over every job, stat, filter, rule, ledger and result, and the old drop-in then schedules nothing.
  • A folder job, a Drive-API job (new client) and a web-drop job each complete a real run.
  • A cron job fires with the window closed (tray), and again after a reboot with "Start with Windows" on.
  • Get-NetTCPConnection -State Listen shows no FileBridge listener outside a Drive Connect.
  • The Panel monitor shows a live run within about 2 s, plus last results and next runs, shows "isn't running" when the app is quit, and has no controls.
  • node test.js and npm test pass.

Changes made during the build

  • Import safety, from review.
    • The Panel's jobs.json is renamed first, then read.
    • Imported jobs wait for their next scheduled time.
    • A job whose scheduled run was still going in Bedrock Panel is held until that run finishes, for 24 hours at most.
    • For 24 hours a follow-up catches late Bedrock Panel writes: it renames a revived jobs.json away again, adds late totals and merges seen-ledgers.
    • A failed import hands the jobs back.
  • Drive sign-in, from review.
    • A dead sign-in shows "not connected".
    • A refresh is retried on a network blip or server error.
    • Only one sign-in listener runs, and a late refresh never brings back tokens after Disconnect.
  • Shell, from review.
    • The API accepts POST only.
    • Development runs keep their data in FileBridge-dev.
    • A startup failure shows a message and exits.
    • The app shuts down cleanly when Windows ends the session.
  • Monitor version. 1.7.5, following the patch-only drop-in rule.
